# Schedule the Workforce

_Files named `references/…` are in this skill's own folder. A file with the same name in another skill's folder is an identical copy: read each reference at most once per conversation._

Give team members recurring responsibilities that run on their own. With the owner, call them recurring responsibilities ("Client Success handles your inbox every day at 10"); in tool calls they are scheduled tasks. Never say triggers, routines or cron jobs.

**One responsibility or the full set.** When called for one responsibility (from the team meeting, or "can someone handle this every Friday?"), propose and create only that one. Use the full default set below only when the owner asks to schedule the team.

**Four states, never blurred:** *proposed* (discussed, not created), *scheduled* (created, and confirmed in the list of scheduled tasks), *ran* (a Briefings row exists for that run), and how it ended, from that row's Result: *succeeded* (Complete), *partly done* (Partial) or *failed* (Failed). Only say "scheduled" after step 5's check, and never say a run happened without its Briefings row. Follow `references/approval-policy.md`.

## Steps

1. **Find the scheduling tools.** Use ToolSearch for scheduling tools (for example "schedule trigger create list"). Go by the tool descriptions. Use only tools that create scheduled tasks that run in fresh sessions (not in-session cron tools, which disappear when the session ends). If none exist, say plainly that scheduled tasks aren't available on this account or surface, explain that the owner can still run each skill by asking, and stop.
2. **Read Workforce Settings** in the Business Brain: time zone, working hours, active departments, and the Schedule section. If the time zone is missing, ask for it.
3. **Check what already exists.** List the owner's existing scheduled tasks (paused ones included). Never create a second task for a responsibility that already has one (match by the task's first-line tag); offer to change its time instead. If the list shows a daily briefing task and a separate inbox triage task that runs within 3 hours of it, offer to combine them ("One morning run" below) before adding anything.
4. **Ask how often, then propose the schedule.** If the owner hasn't already said how often (for example "every Friday") and Workforce Settings / Schedule has no `Check-in frequency` line, ask once: "How often should the team check in: every day (recommended), weekdays only, or another rhythm?" If they don't mind, use every day. Save the answer as a line under Schedule, `- Check-in frequency: every day` (or `weekdays`, or their words), and reuse it next time instead of asking again. Then propose the schedule as a short table (task, when, what it does, departments used). Defaults, at the owner's check-in frequency, adjusted to working hours and active departments:
   - Daily briefing: every day (or the chosen rhythm), 30 minutes before the workday starts. This is the **morning run**: it checks all email first and prepares replies, then briefs the owner, in one run with one notification. Describe it to the owner that way ("every morning your team goes through your email, prepares replies and briefs you").
   - Inbox triage as its own task: not by default. The morning run already checks the inbox, so never create a separate inbox triage task at the same rhythm and time of day. Offer one only as an extra check when the owner wants email looked at more than once a day (one mid-afternoon run), or when the owner wants the inbox checked but no briefing.
   - Weekly marketing plan: Mondays, early morning. Only if a marketing results source is set and Marketing isn't turned off.
   - Invoice review: Fridays, morning. Only if an invoice source is set and Finance isn't turned off.
   - Anything else (Sales follow-ups, an Operations review, a custom member's work): the cadence the owner asked for, with the "Any other responsibility" prompt.
   When proposing the full set, mention that each run uses part of their Claude usage allowance, so fewer runs is fine. Wait for the owner's yes or changes.
5. **Create each scheduled task** with the prompt from `references/scheduled-prompts.md` (keep its first `[AI Workforce task: … | prompt version …]` line), filled in with the owner's Business Brain name. If the owner wants a task to do something extra, add it at the end under a line reading `Owner's additions:` (never edit the stored block itself). Write times in the owner's local time zone. For times on the hour or half hour, move the start a few minutes earlier, and avoid any busy window the tool description warns about, as it advises. Turn on push notifications if the tool supports it. **Then confirm it exists:** list the scheduled tasks again and check each new one is there, enabled, with the right time and a next run. Anything missing or wrong: say so plainly and fix it before going on. Tell the owner once, in one sentence: "These always follow the AI Workforce you have installed, so when you update it they work the new way on their next run; the tasks themselves never change."
6. **Check each result for limits.** If the result says recurring runs won't have the owner's plugins available, say so in plain words: such a run can only report "AI Workforce was not available" and do nothing else, so the responsibility isn't working until that's fixed. The test run in step 10 shows which it is.
7. **Report each task's approval setting** from the tool result in one line. Explain the trade-off only when the full set is being scheduled or the owner asks, plainly and without recommending either: with approval prompts on, an unattended run pauses at the first action that needs approval and may not finish until the owner opens it; with automatic approval, runs finish on their own and rely on the plugin's rules and its send lock (drafts only, no sending, spending, deleting or booking) rather than a prompt to stop them. The owner chooses in the task's settings.
8. **The send lock (say it once, the first time a recurring task is created; skip if Workforce Settings / Schedule already has a `Send lock` line).** Follow `references/approval-policy.md`, "What enforces these rules", and never claim more than it says. In plain words, two layers:
   - **Built in:** "When your team runs on its own, AI Workforce has a lock that refuses the tools that send, forward, delete, share or book, so those runs can only read, draft and queue things for you." If the owner asks how sure that is, say plainly that the lock is new and works wherever Claude runs the plugin's check; the team's rules say the same thing either way, and the second lock below doesn't depend on AI Workforce at all.
   - **Optional, the strongest:** "If you'd like a second lock that doesn't depend on AI Workforce at all, you can block sending in Claude itself: under Customize > Connectors, open your email connection's Tool permissions and set the tools that send, reply, forward and delete to Blocked, leaving search, read and draft allowed. Then nothing in Claude can send from that connection, in any chat, until you change it back." Claude's menus change from time to time; if theirs look different, point them to Anthropic's guide ([Use connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities)) instead of guessing. Never change these settings for the owner, and never suggest "Needs approval" as a lock for unattended runs (nobody is there to answer).
   Save one line under Schedule: `- Send lock: built in` or `- Send lock: built in, and email sending blocked in Claude by the owner <date>` (only what the owner told you they did).
9. **Save the schedule** to Workforce Settings / Schedule, one line per responsibility, with its state: `- Daily briefing: every day 7:23 AM, scheduled, confirmed <date> (includes the inbox check)`. A responsibility discussed but not created is saved as `proposed, not scheduled` with the reason (for example "recurring runs aren't available on this account"). When the morning run covers the inbox, the Inbox triage line reads `- Inbox triage: part of the daily briefing`. Replace `not set` lines; add a line for anything new.
10. **Offer a test run** of the responsibility just created (not a different one), so the owner sees it land in Briefings. A listed schedule only proves it exists; only a Briefings row proves a run happened. If approval prompts are on, warn that the run may wait for them.

## Check recurring responsibilities
Use when the owner says "check my scheduled tasks" or "update my recurring tasks", when a run reported a configuration warning, and after a plugin update. Every recurring task follows the installed plugin's current skill and its rules for scheduled runs (`references/scheduled-run-rules.md`), whatever its stored text says, so **there is never anything to update in a task's instructions**: don't compare stored text with the current blocks, don't offer to rewrite it, and say so plainly if the owner asks ("Your recurring tasks always follow the AI Workforce you have installed, so there's nothing to update. Here's what's scheduled.").

1. **List** the owner's scheduled tasks (include paused ones) and read Workforce Settings → Schedule. AI Workforce tasks are the ones whose instructions start with `[AI Workforce task: … |`.
2. **Show a short list**, one line per task: what it does, when, on or paused, its last run and how that ended (from the task list and the Briefings list). Then only real problems, each with what you'd do:
   - **Schedule:** the time doesn't match the Schedule line. Paused tasks are reported as paused, never treated as a problem to fix.
   - **Duplicates:** two tasks for the same responsibility. Offer to pause the extra one.
   - **Wrong job named:** a task whose first sentence names one responsibility and whose text names a different skill (`references/run-modes.md`, "Which job a recurring task does"). Runs already do the right job; just say so.
   - **Not running:** a task with no Briefings record for its last expected run, or whose last record says AI Workforce was not available.
   Never show raw instructions unless asked.
3. **One morning run.** If there's a daily briefing task and a separate inbox triage task at the same rhythm (both daily, or both on weekdays) whose times are less than 3 hours apart, say: "Your morning briefing now checks your inbox first, in the same run, so the separate inbox check isn't needed any more. Want me to pause it? It stays in your list and you can turn it back on any time." On yes, pause (disable) the inbox triage task, never delete it; list the tasks again and confirm it shows as paused and the briefing task is unchanged; then set the Schedule lines (`- Inbox triage: part of the daily briefing (separate task paused <date>)`). On no, leave both: the briefing uses the separate check's results when they're less than 3 hours old. An inbox triage task 3 hours or more away from the briefing (an extra afternoon check) is not a duplicate; leave it.

## Adding the owner's own instruction to a task
When the owner wants a recurring task to do something extra ("also copy my assistant", "skip Fridays' webinars"): if it's about how the team works in general, save it in the Business Brain instead (`manage-team`), where every run reads it. Only when it truly belongs to one task, add it to that task: read the task's current instructions, add the owner's words at the end under `Owner's additions:` (creating that line if it's missing, and keeping everything before it exactly as it was), and update only the instructions. Then read the task back and confirm the whole text is there, the addition included, and that its schedule, on/off state and settings are unchanged. If the saved text is cut off or anything else changed, put the previous text back, say exactly what's true, and ask before changing a setting. Never do this in a scheduled run.

## Changing or pausing
For "pause the team", "change my briefing time" or "stop inbox triage": list existing tasks, update or disable the matching one, and update Workforce Settings. Never delete a task unless the owner asks for deletion.
