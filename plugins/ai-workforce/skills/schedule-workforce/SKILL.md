# Schedule the Workforce

_`references/…` files are in this skill's folder (same-named files elsewhere are identical copies). Read each once at most, the ones you need together; a file named `if-….md` covers one situation: read it only then._

Give team members recurring responsibilities that run on their own. With the owner, call them recurring responsibilities ("Client Success handles your inbox every day at 10"); in tool calls they are scheduled tasks. Never say triggers, routines or cron jobs.

**One responsibility or the full set.** When called for one responsibility (from the team meeting, or "can someone handle this every Friday?"), propose and create only that one. Use the full default set below only when the owner asks to schedule the team.

**Four states, never blurred:** *proposed* (discussed, not created), *scheduled* (created, and confirmed in the list of scheduled tasks), *ran* (a Briefings row exists for that run), and how it ended, from that row's Result: *succeeded* (Complete), *partly done* (Partial) or *failed* (Failed). Only say "scheduled" after step 5's check, and never say a run happened without its Briefings row. Follow `references/approval-policy.md`.

## Steps

1. **Find the scheduling tools.** Use ToolSearch for scheduling tools. Go by the tool descriptions. Use only tools that create scheduled tasks that run in fresh sessions (not in-session cron tools, which disappear when the session ends). If none exist, say plainly that scheduled tasks aren't available on this account or surface, explain that the owner can still run each skill by asking, and stop.
2. **Read Workforce Settings** in the Business Brain: time zone, working hours, active departments, and the Schedule section. If the time zone is missing, ask for it.
3. **Check what already exists.** List the owner's existing scheduled tasks (paused ones included). Never create a second task for a responsibility that already has one (match by the task's first-line tag); offer to change its time instead. If the list shows a daily briefing task and a separate inbox triage task that runs within 3 hours of it, offer to combine them ("One morning run" below) before adding anything.
4. **Ask how often, then propose the schedule.** If the owner hasn't already said how often (for example "every Friday") and Workforce Settings / Schedule has no `Check-in frequency` line, ask once: "How often should the team check in: every day (recommended), weekdays only, or another rhythm?" If they don't mind, use every day. Save the answer as a line under Schedule, `- Check-in frequency: every day` (or `weekdays`, or their words), and reuse it next time instead of asking again. Then propose the schedule as a short table (task, when, what it does, departments used). Defaults, at the owner's check-in frequency, adjusted to working hours and active departments:
   - Daily briefing: every day (or the chosen rhythm), 30 minutes before the workday starts. This is the **morning run**: it checks all email first and prepares replies, then briefs the owner, in one run with one notification.
   - Inbox triage as its own task: not by default. The morning run already checks the inbox, so never create a separate inbox triage task at the same rhythm and time of day; offer one only as an extra check (one mid-afternoon run), or when the owner wants the inbox checked but no briefing.
   - Commitments review (what the owner promised, and what they're waiting for): not a task. On the owner's yes, save `- Commitments review: on` under Schedule; the morning run does it. A promise the owner names now is an open-work row (`references/run-tracking.md` section 6), never a line here.
   - Urgent-only check: off by default and never in the default set. When the owner asks for it, or says yes to its one offer, create one more task from the Inbox triage block for mid-afternoon, with `Owner's additions:` reading `Urgent-only check.` It reads subjects only, drafts nothing and notifies only when something is urgent.
   - Weekly marketing plan: Mondays, early morning. Only if a marketing results source is set and Marketing isn't turned off.
   - Invoice review: Fridays, morning. Only if an invoice source is set and Finance isn't turned off.
   - Anything else (Sales follow-ups, an Operations review, a custom member's work): the cadence the owner asked for, with the "Any other responsibility" prompt.
   With the full set, mention that each run uses part of their Claude usage allowance. Wait for the owner's yes or changes.
5. **Create each scheduled task** with the prompt from `references/scheduled-prompts.md` (keep its first line, the task tag, as stored), filled in with the owner's Business Brain name. If the owner wants a task to do something extra, add it at the end under a line reading `Owner's additions:` (never edit the stored block itself). Write times in the owner's local time zone, following the tool description's advice on times (for example moving a start off the hour), and turn on push notifications if the tool supports it. **Then confirm it exists:** list the scheduled tasks again and check each new one is there, enabled, with the right time and a next run; anything missing or wrong, say so plainly and fix it before going on. Tell the owner once, in one sentence: "These always follow the AI Workforce you have installed, so when you update it they work the new way on their next run; the tasks themselves never change."
6. **Check each result for limits.** If the result says recurring runs won't have the owner's plugins available, say so in plain words: such a run can only report "AI Workforce was not available" and do nothing else, so the responsibility isn't working until that's fixed. The test run in step 10 shows which it is.
7. **Report each task's approval setting** from the tool result in one line. Explain the trade-off only when the full set is being scheduled or the owner asks, recommending neither: with approval prompts on, an unattended run pauses at the first action that needs approval until the owner opens it; with automatic approval, runs finish on their own and rely on the plugin's rules and its send lock. The owner chooses in the task's settings.
8. **The send lock (say it once, the first time a recurring task is created; skip if Workforce Settings / Schedule already has a `Send lock` line).** Follow `references/if-asked-how-safe.md`, and never claim more than it says. In plain words, two layers:
   - **Built in:** "When your team runs on its own, AI Workforce has a lock that refuses the tools that send, forward, delete, share or book, so those runs can only read, draft and queue things for you."
   - **Optional, the strongest:** "If you'd like a second lock that doesn't depend on AI Workforce at all, you can block sending in Claude itself: under Customize > Connectors, open your email connection's Tool permissions and set the tools that send, reply, forward and delete to Blocked, leaving search, read and draft allowed. Then nothing in Claude can send from that connection, in any chat, until you change it back (replies you approve are then left for you to send)." If their menus look different, point them to Anthropic's guide ([Use connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities)) instead of guessing. Never change these settings for the owner, and never suggest "Needs approval" as a lock for unattended runs (nobody is there to answer).
   Save one line under Schedule: `- Send lock: built in` or `- Send lock: built in, and email sending blocked in Claude by the owner <date>` (only what the owner told you they did).
9. **Save the schedule** to Workforce Settings / Schedule, one line per responsibility, with its state: `- Daily briefing: every day 7:23 AM, scheduled, confirmed <date> (includes the inbox check)`. A responsibility not created is saved as `proposed, not scheduled`, `declined <date>` or `not available on this account`, whichever is true. When the morning run covers the inbox, the Inbox triage line reads `- Inbox triage: part of the daily briefing`. Replace `not set` lines; add a line for anything new.
10. **A test run** of the responsibility just created (not a different one). A listed schedule only proves it exists; only a Briefings row proves a run happened. Called from setup, with the owner present and a tool that starts a task's run now: start one without asking, and report success only when that run's Briefings row exists. Otherwise offer it, and say why it wasn't started (no such tool on this account, or approval prompts are on and the run would wait for them).

## Check recurring responsibilities
Use when the owner says "check my scheduled tasks" or "update my recurring tasks", when a run reported a configuration warning, and after a plugin update. Every recurring task follows the installed plugin (`references/scheduled-run-rules.md`), whatever its stored text says, so **there is never anything to update in a task's instructions**: don't compare stored text with the current blocks or offer to rewrite it, and if asked say "Your recurring tasks always follow the AI Workforce you have installed, so there's nothing to update. Here's what's scheduled."

1. **List** the owner's scheduled tasks (include paused ones) and read Workforce Settings → Schedule. AI Workforce tasks are the ones whose instructions start with the task tag (the first line of each block in `references/scheduled-prompts.md`).
2. **Show a short list**, one line per task: what it does, when, on or paused, its last run and how that ended (from the task list and the Briefings list). Then only real problems, each with what you'd do:
   - **Schedule:** the time doesn't match the Schedule line. Paused tasks are reported as paused, never treated as a problem to fix.
   - **Duplicates:** two tasks for the same responsibility. Offer to pause the extra one.
   - **Wrong job named:** a task whose first sentence names one responsibility and whose text names a different skill (`references/if-old-task.md`). Runs already do the right job; just say so.
   - **Not running:** a task with no Briefings record for its last expected run, or whose last record says AI Workforce was not available.
   Never show raw instructions unless asked.
3. **One morning run.** If there's a daily briefing task and a separate inbox triage task at the same rhythm (both daily, or both on weekdays) whose times are less than 3 hours apart, say: "Your morning briefing now checks your inbox first, in the same run, so the separate inbox check isn't needed any more. Want me to pause it? It stays in your list and you can turn it back on any time." On yes, pause (disable) the inbox triage task, never delete it; list the tasks again to confirm it is paused and the briefing task unchanged; then set the Schedule lines (`- Inbox triage: part of the daily briefing (separate task paused <date>)`). On no, leave both: the briefing reuses the separate check's results when they're under 3 hours old. An inbox task 3 hours or more from the briefing (an extra afternoon check) is not a duplicate; leave it.

## Adding the owner's own instruction to a task
When the owner wants a recurring task to do something extra ("also copy my assistant", "skip Fridays' webinars"): if it's about how the team works in general, save it in the Business Brain instead (`manage-team`), where every run reads it. Only when it truly belongs to one task, add it to that task: read the task's instructions, add the owner's words at the end under `Owner's additions:` (creating that line if it's missing, everything before it exactly as it was), and update only the instructions. Then read the task back: the whole text with the addition, and its schedule, on/off state and settings unchanged. If anything else changed, put the previous text back, say exactly what's true, and ask before changing a setting. Never do this in a scheduled run.

## Changing or pausing
For "pause the team", "change my briefing time" or "stop inbox triage": list existing tasks, update or disable the matching one, and update Workforce Settings. Never delete a task unless the owner asks for deletion.
