# Schedule the Workforce

_Files named `references/…` are in this skill's own folder._

Give team members recurring responsibilities that run on their own. With the owner, call them recurring responsibilities ("Client Success handles your inbox every day at 10"); in tool calls they are scheduled tasks. Never say triggers, routines or cron jobs.

**One responsibility or the full set.** When called for one responsibility (from the team meeting, or "can someone handle this every Friday?"), propose and create only that one. Use the full default set below only when the owner asks to schedule the team.

**Four states, never blurred:** *proposed* (discussed, not created), *scheduled* (created, and confirmed in the list of scheduled tasks), *ran* (a Briefings row exists for that run), and how it ended, from that row's Result: *succeeded* (Complete), *partly done* (Partial) or *failed* (Failed). Only say "scheduled" after step 5's check, and never say a run happened without its Briefings row. Follow `references/approval-policy.md`.

## Steps

1. **Find the scheduling tools.** Use ToolSearch for scheduling tools (for example "schedule trigger create list"). Go by the tool descriptions. Use only tools that create scheduled tasks that run in fresh sessions (not in-session cron tools, which disappear when the session ends). If none exist, say plainly that scheduled tasks aren't available on this account or surface, explain that the owner can still run each skill by asking, and stop.
2. **Read Workforce Settings** in the Business Brain: time zone, working hours, active departments, and the Schedule section. If the time zone is missing, ask for it.
3. **Check what already exists.** List the owner's existing scheduled tasks. Do not create duplicates; offer to update or remove the old ones instead.
4. **Ask how often, then propose the schedule.** If the owner hasn't already said how often (for example "every Friday") and Workforce Settings / Schedule has no `Check-in frequency` line, ask once: "How often should the team check in: every day (recommended), weekdays only, or another rhythm?" If they don't mind, use every day. Save the answer as a line under Schedule, `- Check-in frequency: every day` (or `weekdays`, or their words), and reuse it next time instead of asking again. Then propose the schedule as a short table (task, when, what it does, departments used). Defaults, at the owner's check-in frequency, adjusted to working hours and active departments:
   - Daily briefing: every day (or the chosen rhythm), 30 minutes before the workday starts.
   - Inbox triage (all email; customer support is one part): once a day at the same rhythm, mid-morning. Offer a second, mid-afternoon run only if the owner wants email checked more often.
   - Weekly marketing plan: Mondays, early morning. Only if a marketing results source is set and Marketing isn't turned off.
   - Invoice review: Fridays, morning. Only if an invoice source is set and Finance isn't turned off.
   - Anything else (Sales follow-ups, an Operations review, a custom member's work): the cadence the owner asked for, with the "Any other responsibility" prompt.
   When proposing the full set, mention that each run uses part of their Claude usage allowance, so fewer runs is fine. Wait for the owner's yes or changes.
5. **Create each scheduled task** with the prompt from `references/scheduled-prompts.md` (keep its first `[AI Workforce task: … | prompt version …]` line), filled in with the owner's Business Brain name. Tell the owner once, in one sentence: "These keep their instructions up to date when AI Workforce improves, without touching your schedule or anything you've added to them; say 'don't update my recurring tasks automatically' to turn that off." If the owner wants a task to do something extra, add it at the end under a line reading `Owner's additions:` (never edit the stored block itself), so automatic updates keep it. Write times in the owner's local time zone. For times on the hour or half hour, move the start a few minutes earlier, and avoid any busy window the tool description warns about, as it advises. Turn on push notifications if the tool supports it. **Then confirm it exists:** list the scheduled tasks again and check each new one is there, enabled, with the right time and a next run. Anything missing or wrong: say so plainly and fix it before going on.
6. **Check each result for limits.** If the result shows recurring runs won't have AI Workforce available, say so in plain words ("recurring runs may use a simpler version of your team; your results still land in Notion"); the prompts are written to work either way.
7. **Report each task's approval setting** from the tool result in one line. Explain the trade-off only when the full set is being scheduled or the owner asks, plainly and without recommending either: with approval prompts on, an unattended run pauses at the first action that needs approval and may not finish until the owner opens it; with automatic approval, runs finish on their own and rely on the plugin's written rules (drafts only, no sending, spending, deleting or booking) rather than a prompt to stop them. The owner chooses in the task's settings.
8. **Save the schedule** to Workforce Settings / Schedule, one line per responsibility, with its state: `- Inbox triage: every day 10:23 AM, scheduled, confirmed <date>`. A responsibility discussed but not created is saved as `proposed, not scheduled` with the reason (for example "recurring runs aren't available on this account"). Replace `not set` lines; add a line for anything new.
9. **Offer a test run** of the responsibility just created (not a different one), so the owner sees it land in Briefings. A listed schedule only proves it exists; only a Briefings row proves a run happened. If approval prompts are on, warn that the run may wait for them.

## Check and update recurring responsibilities
Every recurring task follows the installed plugin's current skill and rules for scheduled runs (`references/scheduled-run-rules.md`), so a plugin update changes how every task works on its next run, whatever its stored text says. The four standard tasks also update their stored text on their next run, keeping anything under "Owner's additions", unless the owner changed the stored text itself (`references/run-modes.md`, "Keep the task up to date automatically"; released versions' fingerprints are in `references/prompt-history.md`). The owner can turn the stored-text updates off with "don't update my recurring tasks automatically" (set `Recurring tasks update themselves: no` under Schedule in Workforce Settings, after confirming) or back on. This section is for checking by hand, custom responsibilities, and when the owner has it off.
Use when the owner says "check my scheduled tasks" or "update my recurring tasks", when a run reported a configuration warning, after a plugin update, and whenever `setup-workforce` upgrades the Business Brain. Ask before changing anything.

1. **List** the owner's scheduled tasks (include paused ones) and read Workforce Settings → Schedule.
2. **Compare each AI Workforce task** (its instructions start with `[AI Workforce task: … |`, or its name or instructions mention AI Workforce) with `references/scheduled-prompts.md`, `references/prompt-history.md` and the table in `references/run-modes.md` ("Is the recurring task current?"):
   - **Current:** the task's fingerprint (the script in `references/run-modes.md`) is the current version's in `references/prompt-history.md`. Anything under Owner's additions doesn't count. The version line alone doesn't decide it. Without a shell, compare the text before Owner's additions with the current template by reading (only line endings and trailing spaces may differ).
   - **Older, unchanged:** the fingerprint is an older released version's.
   - **Customized:** anything else, including tasks with no version line. Work out, in plain words, what the owner added or changed compared with the closest released version (`references/scheduled-prompts.md` for the current one; ask the owner about older ones if it isn't obvious).
   - **Schedule:** does the time match the Schedule line? Paused tasks are reported as paused, never treated as a problem to fix.
   - **Duplicates:** two tasks for the same responsibility.
3. **Show the owner a short list**, one line per task: "Inbox triage (every day 11:45): uses older instructions that check only customer emails. Update to the current version?" Up-to-date tasks get one line saying so. For a customized task, say what you'd keep: "You added 'always copy my assistant'; I'll keep that under Owner's additions." Never show raw instructions unless asked.
4. **On yes, update each task in place**, following "Changing a recurring task's instructions safely" in `references/run-modes.md` (capture, back up and read back, re-check, change only the instructions, verify everything, restore if needed). The new instructions are the current template, plus, for a customized task, the owner's changes under "Owner's additions" at the end, exactly as the owner approved them. Never create a new task to replace an old one, and never delete one unless the owner asks; for duplicates, offer to pause the extra one.
5. **Confirm** from the verification: the whole approved text is saved (including Owner's additions; a cut-off or missing section fails), every setting is as before (a paused task stays paused: updating instructions never resumes it), and the next run time still fits the task's existing schedule and time zone. Update the Schedule line only if the owner changed a time. Say plainly what changed and what didn't, using the same wording as `references/run-modes.md` for anything that failed.

## Changing or pausing
For "pause the team", "change my briefing time" or "stop inbox triage": list existing tasks, update or disable the matching one, and update Workforce Settings. Never delete a task unless the owner asks for deletion.
