# Tests

Run everything (no installs, standard Python 3.10+). GitHub Actions (`.github/workflows/ci.yml`) runs all three on every push and pull request (it installs the Claude CLI for `claude plugin validate`, which needs no login):

```
python3 -m unittest discover tests
python3 tools/sync_references.py --check
claude plugin validate . && claude plugin validate plugins/ai-workforce
```

Build the download after any change inside `plugins/ai-workforce` (evals stay out of it):

```
rm download/ai-workforce.plugin && (cd plugins/ai-workforce && zip -qr ../../download/ai-workforce.plugin . -x "*.DS_Store" "evals/*")
```

## Behaviour evals (real Claude runs)

`plugins/ai-workforce/evals/` holds cases that run the plugin in real Claude sessions and grade what Claude actually does: an "ok thanks" approves nothing, an ambiguous number is asked about, instructions inside an email aren't followed, secrets aren't repeated, a dismissed alert stays quiet while a new security alert surfaces, a missing price is asked for rather than invented, a scheduled run drafts but never sends or pays, an invoice isn't marked paid even when the owner asks during a review, the daily briefing goes through the inbox itself and reports once, a quiet day opens with "Handled: nothing" and the reason, first-time setup asks only about the one-click apps (and tells an owner who brings HighLevel up that it comes after the first result), "connect HighLevel" gives the four short steps without calling anything connected, and a run isn't marked partly done while the owner still has HighLevel to connect. Added in 0.9.0: the briefing opens with the work handled and keeps its bookkeeping and old reminders off the first screen, a reply the team can write is a draft and never an approval while a refund the owner's policy leaves to them still is one, the morning run finishes one piece toward the top goal from confirmed facts only and makes none while earlier ones wait, a run that finds another still working stands down (this one has to open a read-when-needed file), a correction from the owner is confirmed in one line before anything is saved (so does this one), and setup's first drafts follow the owner's own style from their sent mail. No Notion or Gmail is connected: each case gives the inputs as text. Every case also checks, without a judge, that one of the team's skills was opened (`type: tool_used`): a reply can look right with no skill loaded, and then the case measured Claude, not this plugin. Three cases did exactly that until 0.9.0 and were rewritten.

They use your Claude login or API key and cost real usage (about $2 for one run of each of the twenty-one cases on Sonnet and about three times that on Opus; the default is 3 runs each), so they aren't in CI. With no `--model` the cases run on Sonnet (`claude-sonnet-5-5` when this was written), whatever model your own chats use. On 0.9.0, on the final text: all twenty-one passed in one pass on Sonnet, and the ten unattended cases passed on Opus (`--model opus`, the model one owner's recurring tasks run on) once one scenario was corrected (below). Run them before each release:

```
cd plugins/ai-workforce && claude plugin eval . --trust-plugin --ablation none --no-publish --max-cost-usd 5
```

While working on one case: `claude plugin eval . --case <name> --runs 1 --ablation none --no-publish --trust-plugin`. Add `--keep-temp` to keep each run's trace, which shows the model used, which skill was opened and which rule files were read.

What writing these cases has taught, so it isn't learned twice:
- **How the judge sees a reply.** A `type: llm` grader sends a small model only the criterion and the reply's last message, never the case's prompt, tells it to be strict and asks for one word, three times. So a criterion has to say who the people and items are, what the test setting allows (with no apps connected a run honestly calls itself Partial and shows a draft as text) and what is *not* a failure ("an Approvals row for the refund is expected"). Criteria with several conditions joined by "and" failed correct replies again and again; one property per grader held. A PASS line that says a reply may "only" say something fails correct replies.
- **What a pattern can check should not go to a judge** (`type: regex`): the Handled line is within the first 500 characters, a key's characters are absent, the briefing isn't signed with the owner's sign-off. Keep patterns narrow: "nothing has been sent" contains "sent", and "Talk soon" also matched a reply explaining why it hadn't signed.
- **Read the failing reply before touching the grader.** Three failures that looked like judge noise in 0.9.0 were real, and the plugin was fixed, not the check: the invoice review queued "mark it paid" and "send this reminder" as approvals; five briefings in eight were signed with the owner's own sign-off; and "3 is fine" was answered without the approvals skill in one run of two.
- **A scenario can be wrong.** The refund case gave a policy that settled the answer ("no refunds after 14 days") and expected a decision anyway. Opus drafted the decline and marked it to read before sending, which is what the rules say. The case's policy now leaves refunds to the owner.
- **A case that never loads a skill only measures Claude.** The secrets case used to be a plain question, where one reply in five quoted the first characters of a key; as an unattended briefing, where the plugin's rule applies, it passes.
- **What the traces showed about weight.** A run opened its skill and then zero to three of its rule files on Sonnet (two to six on Opus), never all the files the skill names. Every unattended run opened `scheduled-run-rules.md`, and the read-when-needed files were opened when their situation came up (an unfinished run, a correction, the quick look). So the size ceilings in `test_plugin.py` are an upper bound, and a rule that must always hold belongs in the skill's own file or in `scheduled-run-rules.md`. With apps connected a run may read more; that has not been measured.
- **Not built yet.** The eval tool can stand in for connected apps (`evals/mocks/`), which would let a case check what the team actually writes to Notion and that no send tool is called. Today every case gives its inputs as text, so none of them sees a real tool being used.

These are for the maintainer. Customers never run anything; their checks happen inside Claude with the `workforce-self-test` skill ("test the workforce").

## What each kind of test proves

Four kinds, never to be confused: **source checks** (the rules are written down), **reference-model tests** (the written design, restated as code, survives hard cases), **tests of real code** (the send lock, which is a program, not an instruction) and **real Claude runs** (Claude actually does it). Only the last kind shows Claude following the rules, and only the behaviour evals, the live self-test and the acceptance checklists below are that kind.

## Live acceptance checklist for 0.9.0

Nothing new in 0.9.0 has been seen on a real account. Before saying it works:

1. **Update reaches the account.** The installed version says 0.9.0.
2. **The page on a phone.** Let the morning run fire, then open the briefing in the Notion app on a phone. Expect the first thing on the page to be the Handled line, then Today and Ready for you; Details and Run record are collapsed sections at the bottom. Count the words outside them (the target is under about 200). If a collapsed section shows up as literal text (`<toggle>`), write down exactly what the page shows: that means the connection wants different wording.
3. **Old and new records together.** The next day's run reads yesterday's record (report first) and an older one (run record first) without calling either unfinished or doubling a run.

Then answer one decision in a brand-new chat with two words ("3 is fine"): the reply should name the item by its AP number and act by the approval rules. Send one draft and delete another. The next morning both are closed ("sent or discarded by the owner") and neither is counted as waiting.
5. **A meeting prep closes itself** the morning after the meeting.
6. **The priority piece.** With goals on Priorities and nothing waiting, expect one "Priority:" row: one page, usable as it is, no invented facts.
